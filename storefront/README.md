# Локальная копия Lady Elka

Статическая сборка публичного сайта. Каждый адрес из sitemap получает отдельный HTML. Товары создаются одним генератором из публичных CSV в Supabase Storage и карты исходных URL `product-routes.json`. Для ёлок и декора используются два варианта разметки одной товарной системы, поскольку их карточки на действующем сайте различаются.

## Запуск

Из корня проекта:

```bash
npm install
npm run dev:storefront
```

По умолчанию сайт откроется на http://localhost:4174/. Если порт занят:

```bash
npm run build:storefront
STOREFRONT_PORT=4175 npm run preview:storefront
```

`build:storefront` читает актуальные CSV из Supabase, создаёт `storefront/dist/` и пересобирает JS/CSS каталога из `src/`. Preview отдаёт только содержимое `dist/`, без подгрузки недостающих файлов с рабочего сайта. `npm run capture:storefront` запускает вспомогательный сервер для пополнения локального снимка старых Taptop-ресурсов; это не production-preview.

## Охват и проверка

- В Supabase: 36 уникальных ID ёлок (34 активных) и 5 ID декора; всего 41 товар.
- Из sitemap и исходных страниц: 42 индексируемых товарных URL. У двух адресов туи один ID с разным написанием slug.
- Сборка создаёт 42 отдельных `index.html` карточек и все 57 маршрутов исходного sitemap.
- Страница `/search` и её пагинация работают от локального индекса всех 57 маршрутов; поиск не обращается к Taptop.
- `python3 storefront/audit/validate_build.py` проверяет все товары, страницы sitemap, поиск, H1 каждой HTML-страницы, цены и характеристики товаров, основные изображения и внутренние ссылки. Результат: `audit/validation-report.json`.
- `audit/build-report.json` содержит подсчёт Supabase, ошибки генерации, отсутствующие описания в источнике и неактивные товары.
- В `audit/screenshots/` лежат снимки оригинала и localhost для ключевых страниц и нескольких разных товаров.
- `sitemap.xml` и `robots.txt` создаются в `dist/`; старые URL сохранены. `/main`, `/catalog-decor`, `/moya-kollekciya` и `/person` обрабатываются локальными редиректами.

## Источники данных и ограничения

- При сборке HTML товаров и каталогов использует Supabase CSV. Товарные страницы пока повторно загружают цены и варианты из Supabase в браузере; каталогам повторная загрузка для отображения не нужна. При открытии сохранённой корзины цены сверяются с Supabase.
- Карточки `/catalog`, `/catalog/landscape-gardening` и `/catalog-tree` теперь генерируются из Supabase CSV с готовыми вариантами, ценами и характеристиками. Товарные страницы пока используют старый JS для выбора вариантов. Подробная карта переноса — [audit/catalog-refactor.md](audit/catalog-refactor.md).
- Manrope и Soyuz Grotesk загружаются из локальных файлов. Старые ссылки на Google Sheets в HTML заменяются публичными CSV Supabase, а фотографии с рабочего домена из CSV открываются из локального снимка. Сетевая проверка основных типов страниц показала только localhost и Supabase.
- Сохранённые изображения и видео лежат локально в `public/` и попадают в `dist/`. Дизайн CSS перенесён в `storefront/styles/`, служебные иконки — в `storefront/assets/widgets/`. Сборка создаёт собственные CSS-пакеты `/f/site-*.css` и не включает системные JS/CSS Taptop. Общие действия меню, модальных окон, FAQ, поиска и слайдера реализованы в `/f/site-runtime.js`.
- Два индексируемых товара, `/tree/kamila` и `/tree/graciya`, имеют только неактивные варианты в Supabase. Исходный сайт скрывает их товарный блок; локальная копия повторяет это поведение. Их HTML и SEO-данные существуют.
- Для 16 товарных URL исходный CSV не содержит описания. Генератор не выдумывает текст: список в `audit/build-report.json`.
- Локальный `local-guard.js` запрещает отправку заказов и вызов платежной функции. Корзина и изменение итоговой суммы проверяются, реальное оформление и платежи не выполнялись.
- Статическая разметка и правила дизайна пока основаны на снимке исходного сайта. Зависимости от его платформенного JavaScript и CSS-файлов в итоговой сборке нет. Точное визуальное совпадение всех адаптивных состояний и форм ещё требует проверки.
- Пять SVG/CSS-адресов возвращают 404 уже на исходном сайте. В локальной сборке битые SVG заменены существующими иконками, отсутствующий CSS удалён; список исходных ошибок в `audit/asset-report.json`. Последняя проверка сборки охватила 292 локальных ресурса.

Timeweb, DNS, рабочий сайт и Supabase не изменялись. Ничего не опубликовано.

## Отправка заявок

Рассрочка, консультации, оптовый прайс и общая форма вопросов используют единый клиент `client/forms.js` и Supabase Edge `lead`. Поля задаёт явная схема `client/lead-schema.js`, сборка добавляет semantic name/data-lead-field. Неизвестная форма с телефоном останавливает сборку, чтобы новая заявка не осталась без подключения. Есть проверка телефона/согласия, sending/success/error, honeypot, защита от двойного submit и повтор с тем же UUID после ошибки.

`npm run build:storefront:production` включает lead endpoint. Preview/локальный guard сохраняют запрет внешних записей. Сам backend и новая таблица `le_leads` развёрнуты; отправка подтверждена тестом только в личку. Frontend сборка сама по себе не публикует сайт. Заказы корзины остаются на `pay`, где собственные хранение и Telegram; административные формы app/ используют свои API.

Аудит всех форм, отчёты и чекпойнты: `agent-context/forms-audit.md`, `forms-report.md`, `progress-forms.md`. Backend/очередь/команды тестов: `supabase/DEPLOY.md` → раздел «Заявки».
